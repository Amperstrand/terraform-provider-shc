## Blocker Checklist Results

### ✅ 1. context.Context on HTTP requests — PASS

`client.go:120` — `doRequest(ctx context.Context, method, path string, ...)` uses `http.NewRequestWithContext(ctx, ...)` (line 127). Context properly threaded through all CRUD methods. `retryOnLock` respects `ctx.Done()` (lines 46-48, 68-70). Resource operations use `withTimeout()` for per-operation deadlines.

**Evidence**: `provider/vm_resource.go:497` — `ctx, cancel := withTimeout(ctx, state.Timeouts, "read", defaultVMReadTimeout)`

### ⚠️ 2. Retry on 429/5xx — **BLOCKER**

Only `retryOnLock` exists (`client.go:35-54`), which retries errors containing "locked" (string match). **No retry on HTTP 429, 500, 502, 503, 504.** No exponential backoff. No jitter.

The Python SHCClient HAS 408 retry with ±20% jitter (per AGENTS.md). The Go client is behind.

**Risk**: A transient SHC API 503 or rate-limit causes immediate Terraform failure with no retry. Production Terraform runs that hit a brief API blip will fail unnecessarily.

**Fix**: Add a `retryOnHTTPError` wrapper around `doRequest` that retries on 429/503 with exponential backoff (base 1s, max 30s, 3 attempts, ±20% jitter). Model on the Python client's existing retry logic. ~30 min.

### ✅ 3. ForceNew on immutable fields — PASS (with advisory)

`hostname` has `stringplanmodifier.RequiresReplace()` (`vm_resource.go:100`). `package_id` uses custom `packageIDUpgrade()` for in-place upgrades. All other resources (snapshot, backup, firewall, rdns) correctly use `RequiresReplace()` on immutable fields.

**Advisory** (not blocking): `template` has no plan modifier. Changing template in HCL after create would show a perpetual diff because Update() doesn't handle template changes. SHC requires reinstall for template changes, which is a destructive operation. File as follow-up issue.

### ✅ 4. Error wrapping — PASS

`%w` verb used correctly throughout: `fmt.Errorf("creating request: %w", err)` (client.go:129), `fmt.Errorf("making request to %s: %w", path, err)` (client.go:141), `fmt.Errorf("VM is locked by a running job after %d retries: %w", lockMaxRetries, lastErr)` (client.go:53). Errors are chain-preserving and actionable.

### ✅ 5. Hardcoded secrets — PASS

No hardcoded credentials. API key comes from provider config (`provider.go:64`). `ssh_key` marked `Sensitive: true` (`vm_resource.go:142`). `nodns_nsec` marked `Sensitive: true` (`vm_resource.go:199`).

### ⚠️ 6. Input validation — **BLOCKER**

`package_id` and `pricing_id` have `positiveInt64()` ✅. `power_state` has custom `powerState()` ✅. But:

- `hostname` — NO validator (no length check, no charset validation, SHC has hostname rules)
- `template` — NO validator (any string accepted, resolved at runtime)
- `size` — NO validator (any string accepted, resolved at runtime)
- `disk_gb`, `ram_mb`, `cpu` — NO validators (negative values accepted client-side)

**Risk**: Invalid inputs produce confusing server-side errors instead of clear client-side diagnostics.

**Fix**: Add validators: `hostname` (1-63 chars, RFC 1123 compliant), `disk_gb`/`ram_mb`/`cpu` (positive int via existing `positiveInt64()`), `size` (regex match `{line}-{cpu}c-{ram}gb`). ~30 min.

### ✅ 7. Resource leaks — PASS

`client.go:143-145` — `defer func() { _ = resp.Body.Close() }()`. Proper cleanup on all code paths.

## Additional Findings

### Must Fix Before Release

**NoDNS code removal**: NoDNS is deeply embedded in the VM resource:
- 4 schema fields: `nodns`, `nodns_zone`, `fqdn`, `nodns_nsec` (`vm_resource.go:72-75, 165-201`)
- `publishNoDNS()` function (`vm_resource.go:457-483`) shells out to Python `shc_toolkit.nodns.provision_dns_for_vm`
- Call site in Create lifecycle (`vm_resource.go:382-398`)
- State persistence references (`vm_resource.go:516-517, 608`)

**Decision**: Remove all NoDNS code. It belongs at a provisioning layer above TF, not in the provider itself. User declared it out of scope.

### Potential Blocker (verify during Phase 2 E2E)

**`waitForProvisioning` waits for `provisioning_state == "ready"`** (`vm_resource.go:428`). AGENTS.md Lesson #1 states this NEVER happens — VMs stay in "provisioning" forever. If true, every Create call times out after 10 minutes (120 attempts × 5s).

However, acceptance tests (TF_ACC) passed on Jul 31, including `TestAccVMResource_Basic` which asserts `provisioning_state == "ready"`. This suggests either:
1. VMs DO reach ready on the plans used in acceptance tests (Dev VPS plans)
2. The AGENTS.md lesson applies to specific plan types (NVMe Starter) but not others
3. The lesson was discovered after Jul 31 and is a regression

**Action**: Verify during Phase 2 bridge E2E. If the test VM reaches ready → no fix needed. If it times out → the wait logic must be changed to check `service_status == "active" && ips != []` per AGENTS.md Lesson #1.

### Advisory (file as GitHub issues, don't block)

1. **Template changes not handled in Update()**: Changing `template` after create produces perpetual diff. File as follow-up.
2. **No structured logging**: No `tflog` usage for debug-level diagnostics. Hetzner uses structured logging extensively. File as follow-up.
3. **No custom plan modifiers for `term`**: Term changes trigger an API call but there's no custom plan modifier documenting the behavior. File as follow-up.
